## 📝 Problem Statement
One real account (the owner): with many plants it is easy to lose track of what to do and when. Evidence is thin (no episode), which the brief records; the owner treats it as real (D11).

## 📝 Proposed Solution
- Pure functions in `services/calendar/`: `windowsFor(timing, frostDates, year) → Window[]`. Nothing derived is persisted.
- Frost dates stored on the garden as two date-only columns plus an optional coarse `region` slug. `StaticFrostDateProvider` maps region → suggested dates; manual override always wins.
- `operations` stored user data: one operation → many plantings.
- Alternatives rejected: storing generated tasks (violates R05, drifts when frost dates change); a generic reminders/cron route (Ask First in `AGENTS.md`).

## 📝 Architecture
- `services/calendar/` (pure, new), `services/gardens/garden.service.ts` gains `setFrostDates`, `services/operations/operation.service.ts` (new), port `FrostDateProvider` + `StaticFrostDateProvider` adapter registered in the container.
- Task list endpoint composes: plant list (catalogue spec) + crop timing + garden frost dates → windows. Depends on the catalogue spec being merged; frost dates and operations do not depend on the grid spec.

## 📝 Data Model
- `gardens` adds `last_spring_frost date null`, `first_autumn_frost date null`, `region text null` (coarse slug, never address/coordinates).
- Crop timing (catalogue columns, added by this spec's migration if the catalogue spec has not): `sow_from_offset_days`, `sow_until_offset_days` (relative to last spring frost, may be negative), `plant_out_from_offset_days`, `plant_out_until_offset_days` (same anchor), `prune_from_month`, `prune_until_month` (1–12, frost-independent) — all nullable, with `timing_source` NOT NULL when any is set.
- `operations`: `id`, `gardenId`, `type`, `date` (date-only), `isDone` boolean (future date → planned; past/today → done is user-chosen), timestamps. `operation_plantings`: `operationId`, `plantingId`. Owned through the garden; plantings must belong to the same garden.
- Migration + snapshot for each. No sensitive data beyond coarse region.

## 📝 API Contracts
- `PUT /api/gardens/:id/frost-dates` `{ lastSpringFrost?: YYYY-MM-DD, firstAutumnFrost?: YYYY-MM-DD, region?: slug }` → garden. Validation: valid calendar dates, spring before autumn, region in provider list. Invalid → 422 with `fieldErrors`, nothing saved.
- `GET /api/frost-regions` → `[{slug, name, lastSpringFrost, firstAutumnFrost, source}]` (suggestions only).
- `GET /api/gardens/:id/tasks?year=` → `{ tasks: [{plantingId, cropId, kind: sow|plant-out|prune, from, to, source}] , needsFrostDates: boolean }`. Without frost dates, frost-dependent tasks are omitted and `needsFrostDates` is true; prune windows (month-based) still appear.
- `GET/POST /api/gardens/:id/operations`; POST `{ type, date, plantingIds: uuid[1..MAX_PLANTINGS_PER_OPERATION] }` → 201; `DELETE …/operations/:opId`; `PATCH` toggles `isDone`. No assignee, notes or photo field exists. Unknown/foreign planting id → 404 for the whole request.

## 📝 UI/UX
Task list page: top banner asking for frost dates when missing (region picker prefills editable date fields); grouped by month; each task shows crop, window and its source. Operations section on the same page: list sorted by date with planned/done chips; "Record operation" form with type, date, and multi-select of plants (select all). States: loading, empty (no plants → link to catalogue), error. Dates shown in the user's locale; keyboard-operable multi-select.

## 📝 Edge Cases & Failure Scenarios
- Autumn frost before spring frost or feb-29 values: rejected with field errors.
- Southern Hemisphere or late-frost years: windows are offsets from the supplied dates, so they just work; a window crossing year-end is returned as one window with `to` in the next year.
- Crop with no timing: no task, no guessed date (R03).
- Planting deleted after being referenced by an operation: link row cascades; operation with zero plantings is deleted in the same transaction.
- Frost dates changed while viewing: next fetch recomputes; nothing stale is stored.
- Provider fails: manual entry still works (static provider cannot fail; contract documented for later adapters).

## 📝 Risks & Impact Review
- `AGENTS.md` change: adds the `operations` concept and optional-bed planting (shared with the catalogue spec). Hard to reverse: the `operations` table shape and the offset-based timing columns; mitigated by keeping both minimal and nullable.
- Direction call (owner): whether tasks being read-only is enough (Q07 of the brief is open); no evidenced rule violation.
- Pruning correctness is the owner's risk (D04); each window shows its source.
- Operations of spraying carry no advice (D09), avoiding safety liability.

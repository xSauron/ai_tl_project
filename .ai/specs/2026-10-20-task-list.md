# Task list, frost dates and operations

Serves E02-S02 (#24), E02-S04 (#26), E02-S05 (#27) of epic E02 (#19). Depends on `2026-10-20-catalogue.md` (`Crop` data) and `2026-10-20-garden-grid.md` Phase 1 (plant list).

- **Changes:** 2026-10-21 — owner grilling session on #19 (Q1–Q24, all agent recommendations accepted; log `.ai/runs/2026-10-21-grill-e02-specs.md`): frost dates as `MM-DD`, timing windows in their own table with a per-window anchor, `sow-indoors`, tasks grouped by crop, rolling 12-month range, derived done status, operation history kept on planting delete, more operation types.

## 📝 TLDR
The owner loses track of sowing, planting-out and pruning dates across many plants. **Proposed (future):** the owner sets the usual last-spring and first-autumn frost days (`MM-DD`, no year) per garden; the app derives sowing, planting-out and pruning windows from the catalogue's timing windows and those days without storing them (R05), grouped by crop; and one operations list records what was or will be done, once for many plants (D14, R09). A done operation inside a task's window marks that task done, computed on read.

## 📝 Problem Statement
One real account (the owner): with many plants it is easy to lose track of what to do and when. Evidence is thin (no episode), which the brief records; the owner treats it as real (D11).

## 📝 Proposed Solution
- Pure functions in `services/calendar/`: `occurrences(window, frostDays, range) → { from, to }[]` and `deriveTasks({ plantings, windows, frostDays, doneOperations, today }) → { tasks, missingFrostDates }`. Nothing derived is persisted.
- Frost days stored on the garden as two nullable `MM-DD` values plus an optional coarse `region` slug. `StaticFrostDateProvider` maps region → suggested days; manual override always wins.
- `operations` stored user data: one operation → many plantings.
- Alternatives rejected: storing generated tasks (violates R05, drifts when frost dates change); a generic reminders/cron route (Ask First in `AGENTS.md`); a stored "task done" flag (violates R05; the operation already records the fact); timing as columns on `crops` (cannot hold a spring and an autumn sowing of the same crop, G3); full dates with a year for frost (ambiguous across years, G1).

## 📝 Architecture
- `services/calendar/` (pure, new: `frost-days.ts`, `timing-windows.ts`, `tasks.ts`, `today.ts`), `services/gardens/garden.service.ts` gains `setFrostDates`, `services/calendar/task.service.ts` (reads, composes, never writes), `services/operations/operation.service.ts` (new), port `FrostDateProvider` + `StaticFrostDateProvider` adapter registered in the container.
- Task list endpoint composes: plant list (garden-grid Phase 1) + crop timing windows (catalogue) + garden frost days + the garden's done operations → tasks. Depends on the catalogue spec being merged; frost dates and operations do not depend on the grid spec.

## 📝 Data Model
- `gardens` adds `last_spring_frost char(5) null`, `first_autumn_frost char(5) null` (`MM-DD`, check `^(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])$`; `02-29` rejected by Zod), `region text null` (coarse slug, never address/coordinates).
- `crop_timing_windows` (table created by the catalogue spec's migration; this spec defines its meaning and owns the derivation): `id`, `crop_id` → `crops` (cascade), `kind` (`sow-indoors | sow | plant-out | prune`), `anchor` (`spring-frost | autumn-frost | calendar`), `from_offset_days`, `until_offset_days` (`smallint`, frost anchors only, may be negative, `from ≤ until`), `from_day`, `until_day` (`char(5)` `MM-DD`, `calendar` only; `until < from` means the window crosses New Year), `source`, `source_url` NOT NULL. A check enforces exactly one bound pair matching the anchor. A crop with no rows gets no tasks (R03).
- `operations`: `id`, `gardenId` (cascade), `type` (`sow-indoors | sow | plant-out | prune | spray | fertilize | harvest | other`), `date` (date-only), `isDone` boolean (a date after today in `APP_TIME_ZONE` is always planned: `isDone = true` with such a date is rejected; today or earlier is user-chosen), timestamps. `operation_plantings`: `operationId` (cascade), `plantingId` (cascade). Owned through the garden; plantings must belong to the same garden. An operation keeps its row when its last link goes (G6).
- Named constants in `validators/limits.ts`: `MAX_PLANTINGS_PER_OPERATION = MAX_PLANTINGS_PER_GARDEN`, `TASK_LOOKBACK_DAYS = 30`, `TASK_LOOKAHEAD_MONTHS = 12`; `APP_TIME_ZONE` in `core/src/services/calendar/today.ts`.
- Migration + snapshot for each. No sensitive data beyond coarse region.

## 📝 Derivation rules (pure, tests first)
- **Frost day → date in a year:** `MM-DD` + year. Windows are resolved for every year that can overlap the range (today's year − 1 to + 1), then clipped to the range by overlap (a window that overlaps the range is returned whole).
- **Frost anchors:** `from = frostDay(year) + from_offset_days`, `to = frostDay(year) + until_offset_days`.
- **Calendar anchor:** `from = from_day` of the year; `to = until_day` of the same year, or of the next year when `until_day < from_day`.
- **Missing frost day:** windows anchored to it are skipped and the day is listed in `missingFrostDates`. Calendar windows always appear.
- **Grouping:** one task per `(cropId, kind, occurrence)` with every planting of that crop in the garden; `plantingCount`, `plantingIds`.
- **Perennials (G15):** for crops of kind `bush`/`tree`, a planting is dropped from a `sow-indoors`/`sow`/`plant-out` task once any done operation of that type links it; a task left with no plantings disappears.
- **Done (G18):** `doneCount` = plantings of the task linked to a done operation of the same type dated inside the occurrence (inclusive). `isDone = doneCount = plantingCount`.
- **Overdue:** a task occurrence with `to < today` and `isDone = false` is `overdue`; an operation with `isDone = false` and `date < today` is `overdue` (G8). Labels only.

## 📝 API Contracts
- `PUT /api/gardens/[id]/frost-dates` `{ lastSpringFrost?: MM-DD | null, firstAutumnFrost?: MM-DD | null, region?: slug | null }` → garden. Validation: valid month-day (no `02-29`), region in the provider list. Spring after autumn in the calendar is allowed (Southern Hemisphere). Invalid → 422 with `fieldErrors`, nothing saved.
- `GET /api/frost-regions` → `[{slug, name, lastSpringFrost, firstAutumnFrost, source}]` (suggestions only).
- `GET /api/gardens/[id]/tasks` → `{ today, range: { from, to }, missingFrostDates: ("spring" | "autumn")[], tasks: [{ cropId, kind, from, to, plantingIds, plantingCount, doneCount, isDone, isOverdue, source, sourceUrl }] }`, sorted by `from`. No query parameters.
- `GET/POST /api/gardens/[id]/operations`; POST `{ type, date, isDone, plantingIds: uuid[1..MAX_PLANTINGS_PER_OPERATION] }` → 201; `DELETE /api/operations/[id]`; `PATCH /api/operations/[id]` `{ isDone }` only (no other field is editable, G24); setting `isDone = true` on an operation dated after today is rejected with 422, the same rule as POST. The list returns `{ id, type, date, isDone, isOverdue, plantingIds, plantingCount }`. No assignee, notes or photo field exists; unknown keys are rejected. Unknown/foreign planting id → 404 for the whole request.

## 📝 UI/UX
Task list page `(app)/gardens/[gardenId]/tasks`: top banner naming each missing frost day (region picker prefills editable `MM-DD` fields); tasks grouped by month, each showing crop, kind, window, "n plants", done state (`12/30`) or an overdue label, and its source link; "Record operation" opens the operation form prefilled with the task's type, today and its `plantingIds`, editable before saving. Operations section on the same page: list sorted by date with planned / done / overdue chips, a done toggle and delete (`ConfirmDialog`); "Record operation" form with type, date, done, and multi-select of plants (select all). States: loading, empty (no plants → link to catalogue), error. Dates shown in the user's locale; keyboard-operable multi-select.

## 📝 Edge Cases & Failure Scenarios
- Invalid month-day (`02-30`, `13-01`) or `02-29`: rejected with field errors.
- Southern Hemisphere or late-frost places: windows are offsets from the supplied days, so they just work; no spring-before-autumn rule.
- A window crossing New Year (calendar `11-01`–`02-28`, or a frost offset past 31 December) is one task with `to` in the next year.
- A window overlapping the range edge is returned whole; the same window can appear for two years when both occurrences overlap the 13-month range.
- Crop with no timing windows: no task, no guessed date (R03).
- Planting deleted after being referenced by an operation: its links go; the operation stays with fewer (possibly zero) plantings (G6).
- Done operation dated one day before the window opens: does not count (G18).
- A perennial planted last year: no new `plant-out` task, only `prune` (G15). A vegetable kept on the list: tasks again next year (G16).
- Frost days changed while viewing: next fetch recomputes; nothing stale is stored.
- Midnight in Poland while the server clock is still on the previous UTC day: `today` uses `APP_TIME_ZONE` (G23).
- Provider fails: manual entry still works (static provider cannot fail; contract documented for later adapters).

## 📝 Risks & Impact Review
- `AGENTS.md` change: the `operations` concept and optional-bed planting landed in PR #38; this revision updates the operation types and frost-day format there.
- Hard to reverse: the `operations` table shape and `crop_timing_windows`; mitigated by keeping both minimal.
- Derived done status depends on the owner recording operations with the matching type; a spray or `other` operation never clears a task (by design).
- Pruning correctness is the owner's risk (D04); each window shows its source.
- Operations of spraying carry no advice (D09), avoiding safety liability.
